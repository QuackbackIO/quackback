# Review of the v2 extension plans

Reviewed 2026-09-19 against checkout `eb79147670c8872a456c2a0b817bcbaa4c626650`.

**Verdict: the capabilities are achievable, and the fork architecture can support continued upstream upgrades, but the plans are not implementation-ready unchanged.** Separate migration ledgers, sidecar tables, fork-owned modules, and a separate control tower are sound choices. Several proposed integration contracts are incomplete or incorrect. Keeping edits small does not by itself preserve upstream behavior.

Scope: all six feature plans in `plans/v2` (10–60), plus that directory's conventions, decisions, seam registry, README, and embedded prior-review context. There are five product extensions plus the RBAC foundation. No plans outside `plans/v2` were reviewed. This is a static code/design review, not a runtime certification. No implementation was changed. Dependencies are not installed in this checkout; DB, AWS, browser, load, and upgrade rehearsals were not run. The `apps/` and `packages/` trees have no diff from the plans' cited upstream baseline `780a7b577`.

## Codebase orientation

- Bun monorepo. `apps/web` is the TanStack Start/React application and server; `packages/db` owns Drizzle schema, SQL migrations, permission catalogue and seeding; `packages/widget` owns the embed SDK. Shared packages cover IDs, email, and logging.
- Server functions and REST/MCP handlers call domain services. Authorization combines permission sets, legacy teammate roles, session audience, and object-level policies. These are distinct checks; replacing one does not automatically fix the others.
- Conversations and tickets can form a pair but retain independent assignment fields. Workflows, ticket activity, notifications, SLA state and realtime publication have their own side effects. Existing service methods are not generally a single transactional extension API.
- Pooled tenancy resolves a workspace from the host/control registry, binds request-local DB/config/secrets, and uses per-workspace databases. Runtime schema checks and the fleet migrator track the upstream migration lineage.
- CI maintains permission mirrors and authorization, dependency, migration, and module-state contracts. These help detect structural drift but do not prove the fork's authorization or workflow semantics.

## Per-plan assessment

- **10 — RBAC/personas:** necessary and feasible; highest security dependency. The proposed MCP fix does not yet cover all authorization paths. Define credential row scope and role-assignment ownership explicitly.
- **20 — Control tower:** separate process and per-human tenant OAuth are appropriate. Provisioning privacy, role synchronization, identity mappings, API contracts and rollout behavior need revision. AWS and SSO spikes remain real gates.
- **30 — Tiered support/hub:** reuse is sensible, but the proposed lead merge fails for the exact requester type it is intended to support. Escalation needs durable concurrency/recovery semantics. Ordinary assignment paths can bypass tier invariants.
- **40 — Account actions:** the configurable HTTP contract and explicit unknown state are good foundations. Resolve authorization contradictions, a DB-check conflict, unsafe response classification and incomplete recovery before implementation.
- **50 — Prioritization:** lowest implementation risk. SQL-derived scoring and a sidecar/history model fit this repository. Formula decisions and framework-switch semantics still need agreement; portfolio API and optional revenue caching are underspecified.
- **60 — Announcements:** feasible with isolated routes and a shared feed. Identity refresh, resolved-status sourcing and durable audit need correction. Some advertised parity/freshness guarantees are stronger than the design delivers.

## Findings requiring changes

P1 means fix before the affected feature ships. P2 means resolve before committing its implementation contract. These are design findings, not claims that the unimplemented features are currently exploitable.

### F1 — P1: the separate migration lineage is not yet a complete production rollout

**Plan:** [plans/v2/02-fork-conventions.md:61](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/02-fork-conventions.md:61) and [plans/v2/20-control-tower.md:211](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/20-control-tower.md:211).

Three gaps remain:

1. The production Docker image copies only `packages/db/drizzle` to `/app/drizzle`; it does not copy `drizzle-fork`. Migration bundles also need a fork migration path that survives bundling. Merely adding a call to `runMigrations` is insufficient. Evidence: [apps/web/Dockerfile:111](/Users/adamstavely/Documents/GitHub/quackback/apps/web/Dockerfile:111), [packages/db/src/schema-version.ts:48](/Users/adamstavely/Documents/GitHub/quackback/packages/db/src/schema-version.ts:48).
2. `fork-migrate` is defined as applying **only fork SQL**, but permission catalogue reconciliation runs in `seedSystemData`, not in SQL. With no upstream migration change, the upstream fleet runner skips that tenant, so new fork keys and Manager exclusions may never reach its DB. Evidence: [apps/web/src/lib/server/fleet/schema-state.ts:120](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/fleet/schema-state.ts:120), [packages/db/src/seed-system.ts:47](/Users/adamstavely/Documents/GitHub/quackback/packages/db/src/seed-system.ts:47).
3. The runtime schema floor checks only the upstream ledger. `fork-migrate` iterates active tenants, leaving suspended tenants needing an explicit catch-up before resume. A partial fork rollout can otherwise admit a workspace that passes the upstream floor but lacks fork tables. Evidence: [apps/web/src/lib/server/fleet/schema-floor.ts:1](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/fleet/schema-floor.ts:1).

**Correction:** include fork SQL and provisioner executables in the production artifact; run catalogue reconciliation on fork-only releases; record/verify the fork schema floor; make resume catch up before activation. Add these seams and deployment steps to the registry. Rehearse a fork-only permission release, a suspended-then-resumed tenant, partial failure, and previous-code/new-schema coexistence.

### R1 — P1: the MCP permission map does not enforce the full RBAC contract

**Plan:** [plans/v2/10-rbac-persona-extensions.md:149](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/10-rbac-persona-extensions.md:149).

`forkMcpToolGate(auth, def.name)` knows only the tool name and supports key/any-of/dispatch entries. That cannot correctly authorize arguments of tools such as `triage_post`: an actor allowed to set status must not thereby gain the ability to set the owner. The handler calls `updatePost` with attribution, not a permission-bearing policy actor. Likewise, a `dispatch` marker alone does not add permission checks inside `search`/`get_details` branches. Evidence: [apps/web/src/lib/server/mcp/tools/posts.ts:150](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/mcp/tools/posts.ts:150), [apps/web/src/lib/server/mcp/tools/search.ts:149](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/mcp/tools/search.ts:149), [apps/web/src/lib/server/domains/posts/post.service.ts:349](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/posts/post.service.ts:349).

There are also paths outside that gate:

- MCP resources are registered separately and check scopes rather than custom-role permissions. For example, `quackback://members` bypasses `member.view` unless explicitly patched. [apps/web/src/lib/server/mcp/server.ts:33](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/mcp/server.ts:33)
- `get_ticket` reads the ticket and messages without an actor. Adding `ticket.view` at registration still does not limit it to the caller's teams. [apps/web/src/lib/server/mcp/tools/tickets.ts:149](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/mcp/tools/tickets.ts:149)
- REST's shared service-actor builder and several inline actors omit `permissions`, leaving domain checks able to fall back to the legacy preset. [apps/web/src/lib/server/domains/api/service-actor.ts:16](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/api/service-actor.ts:16), [apps/web/src/lib/server/policy/authorize.ts:21](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/policy/authorize.ts:21)
- Service principals explicitly bypass ticket/conversation team visibility, so copying a creator's role bundle does not copy their row scope. [apps/web/src/lib/server/policy/tickets.ts:45](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/policy/tickets.ts:45), [apps/web/src/lib/server/policy/conversations.ts:41](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/policy/conversations.ts:41)

**Correction:** inventory tools, argument-dependent branches, resources, REST actor builders and object-access checks. Make the gate argument-aware and require every affected field's permission. Thread resolved permissions through all actors; add explicit row checks where services do not perform them. Decide whether API keys are deliberately workspace-wide or inherit team restrictions. Tests must include direct IDs outside the caller's team and mixed allowed/forbidden mutation fields, not just tool-name coverage. Additional seams are necessary.

### C1 — P1: provisioned portals would default to public

**Plan:** [plans/v2/20-control-tower.md:155](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/20-control-tower.md:155) uses upstream `DEFAULT_PORTAL_CONFIG`, while D-N5 requires every app portal to be private.

The actual default is `access.visibility: 'public'` and `features.allowAnonymous: true`. Omitting `authConfig.openSignup` does not change portal visibility. Evidence: [apps/web/src/lib/server/domains/settings/settings.types.ts:370](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/settings/settings.types.ts:370). Verify unauthenticated access to boards, support and help-center routes is denied. Make provisioning/resume fail closed on a partially configured app.

### C2 — P1: role synchronization lacks assignment ownership and fail-closed reconciliation

**Plan:** [plans/v2/20-control-tower.md:191](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/20-control-tower.md:191), [plans/v2/10-rbac-persona-extensions.md:176](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/10-rbac-persona-extensions.md:176).

The tower identifies managed assignments by whether their template is currently named by a tower role. That is not sufficient provenance: a manually assigned copy of the same template is indistinguishable; deleting or retargeting the tower role can orphan the old grant. A Tier bundle also needs a per-app **team mapping**, but the proposed tower tables contain only a template key. Plan 30 explicitly requires the missing mapping.

The write must also reconcile default preset assignments, not merely append custom assignments. Otherwise a principal initialized as `member` may retain Manager alongside Fleet Observer. At the opposite edge, an active `member` left with zero workspace assignments falls back to Manager. `permissionsForPrincipal` makes that fallback explicit. Evidence: [apps/web/src/lib/server/policy/permissions.ts:58](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/policy/permissions.ts:58), [apps/web/src/lib/server/domains/principals/principal.factory.ts:357](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/principals/principal.factory.ts:357).

`canInTeam` must identify real system-role assignments rather than interpreting legacy `member` as Manager; all the custom personas use that same legacy role.

**Correction:** persist tower-owned grant provenance and per-app team mappings; atomically reconcile desired grants, preset rows and legacy status. Define zero-role behavior, deletion, demotion, and local-versus-tower ownership. Test initial Observer provisioning, last-role removal, template replacement, a manual grant of the same role, and upstream role changes clearing extra hats. Template sync is currently add-only, so it cannot repair excess privileges as the tower plan claims.

### C3 — P2: tower identity and feature contracts are not fully specified

**Plan:** [plans/v2/20-control-tower.md:220](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/20-control-tower.md:220), [plans/v2/20-control-tower.md:327](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/20-control-tower.md:327), [plans/v2/20-control-tower.md:512](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/20-control-tower.md:512).

The plan uses one `idp_subject` for app pre-linking and says tenant `id_token.sub`/email must match the tower user. It needs an explicit mapping between the tower identity, provider/broker identity, tenant user ID and tenant principal ID; these are not interchangeable IDs. The local MCP handler treats token `sub` as the tenant `userId`. Evidence: [apps/web/src/lib/server/mcp/handler.ts:98](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/mcp/handler.ts:98). Do not make email equality the implicit identity-linking contract.

There are also concrete feature mismatches:

- Tower portfolio expects `list_prioritized_posts` and scores in `get_details`; plan 50 provides only `get_post_prioritization` and explicitly avoids extending core DTOs.
- Fleet Observer has `announcements.view`, but all announcement management/list tools require `announcement.manage`, which Observer lacks. The tower maps announcement reads to a write scope; plan 10 says Observer tokens should be read-only.
- Plan 20 runs `sync-members` as a privileged provisioner job; plans 10/30 also describe it calling tenant MCP as the human admin. Choose which operations use each authority, including first provisioning and IdP-driven revocation when no human admin token is available.

**Correction:** publish a shared contract for identity mapping, capabilities → exact tools/arguments → permissions/scopes, and synchronization authority. Add the missing read/list APIs or narrow the tower's promised capabilities. Define a maximum revocation delay for IdP group removal; login-only claim refresh does not provide prompt revocation of an already active session.

### T1 — P1: the email-only requester claim calls a helper that rejects email-only leads

**Plan:** [plans/v2/30-tiered-support.md:310](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/30-tiered-support.md:310) selects anonymous principals with `userId IS NULL`, then calls `mergeLeadIntoUser`.

That helper rejects the lead when `!lead.userId` and later tears down its anonymous user identity. Cold inbound email intentionally creates principals without a user row. Consequently the proposed hub login cannot recover those emailed requests. Evidence: [apps/web/src/lib/server/domains/users/user.merge.ts:65](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/users/user.merge.ts:65), [apps/web/src/lib/server/domains/conversation/conversation.email-cold-inbound.ts:106](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/conversation/conversation.email-cold-inbound.ts:106).

**Correction:** add a fork claim service for standalone email leads, reusing the transactional re-point registry but using the appropriate principal-only teardown. Verify the session's email ownership, preserve blocked/unverified provenance, handle collisions and concurrent claims, and test both OTP and magic-link flows. Do not bypass the existing helper's guard indiscriminately.

### T2 — P1: escalation is not idempotent or concurrency-safe as described

**Plan:** [plans/v2/30-tiered-support.md:137](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/30-tiered-support.md:137).

The service reads `expectedFromTeamId`, then performs independent conversation assignment, ticket assignment, SLA, ledger, note and watcher writes. It inserts the idempotency row near the end. If it crashes after ticket assignment but before the ledger/watch, a retry can conflict with the original from-team or take the already-on-target no-op, leaving no ledger or watcher. Concurrent requests can both pass the initial check and interleave their writes. Repeating steps 7–9 is not intrinsically idempotent: notes and subscriptions have different behavior, and automatic distribution has state.

Upstream `assignTeam` no-ops when already on the requested team and publishes separate side effects; `assignTicket` performs its own update and fire-and-forget events. Evidence: [apps/web/src/lib/server/domains/conversation/conversation.service.ts:1542](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/conversation/conversation.service.ts:1542), [apps/web/src/lib/server/domains/tickets/ticket.service.ts:744](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/tickets/ticket.service.ts:744).

**Correction:** claim a durable operation before mutating, serialize/CAS the relevant assignment state, persist the chosen target/agent and completed steps, and make recovery finish the same operation. Alternatively introduce narrowly scoped transaction-aware primitives and a transactional outbox. Include all ordinary assignment writers in the concurrency design; an advisory lock taken only by the fork does not constrain upstream writers. Kill/retry and two-competing-escalations tests are mandatory.

### T3 — P1: ordinary routing/assignment paths can invalidate tier and SLA guarantees

**Plan:** [plans/v2/30-tiered-support.md:109](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/30-tiered-support.md:109), [plans/v2/30-tiered-support.md:207](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/30-tiered-support.md:207).

The ticket wins over the conversation when both have teams. But upstream workflow `assign_team` changes only the conversation. Once a ticket has a non-null team, the proposed fallback cannot keep its tier correct after a later conversation assignment. Normal assignment UI/API paths also do not update the fork ledger. Historical conversation-only tier changes cannot be reconstructed from ticket activity.

Auto-routing is checked only when enabling tiers and can subsequently be re-enabled; a warning does not enforce the stated invariant. Seeded intake workflows start disabled. Direct unpaired tickets and manual/API creation need explicit intake rules rather than assuming every creation emits a usable conversation trigger.

Finally, `assignTicket` stamps `firstResponseAt` for a human teammate, even if the only action was escalation. Thus “never reapply active SLA” is not enough to establish unchanged first-response behavior. Evidence: [apps/web/src/lib/server/domains/workflows/action.executor.ts:479](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/workflows/action.executor.ts:479), [apps/web/src/lib/server/domains/tickets/ticket.service.ts:774](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/tickets/ticket.service.ts:774), [apps/web/src/lib/server/domains/tickets/ticket.lifecycle.ts:47](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/tickets/ticket.lifecycle.ts:47).

**Correction:** define and enforce how every assignment/intake path interacts with tier mode. Either constrain those paths or route them through a shared invariant-preserving operation. Explicitly decide whether escalation counts as a first response. Capture enough history for per-tier metrics; test the ticket/conversation pair after ordinary assignments and delayed workflow execution, not only fork escalation.

### A1 — P1: account-action authorization contradicts the team-scoped prerequisite

**Plan:** [plans/v2/40-support-account-actions.md:210](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:210), [plans/v2/40-support-account-actions.md:408](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:408), and phase 6 at [plans/v2/40-support-account-actions.md:438](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:438).

Plan 10 says workspace-wide custom grants of `account.request`/`account.execute` are inert and fork checks must use `canInTeam`. Plan 40 still specifies a workspace-wide `can()` fallback and defers team enforcement to phase 6, even though plan 30 already requires team RBAC. This would allow an early release to run actions through a grant that plan 10 explicitly declares inert.

Static `requireAuth({permission: account.execute})` also rejects a valid team-only grant before the team resolver runs, unless a redundant workspace grant happens to be present. The normal Tier template supplies both, but phase 6 explicitly promises team-only operation.

**Correction:** use team-aware authorization from the first runnable account-action phase; remove the fallback. Gate entry on authenticated dashboard/ticket access, then authorize the particular team/tier in the domain. Explicitly enforce ticket visibility on direct run, approval, cancellation and unknown-outcome resolution. Record how approval behaves if the ticket moves to a different owning team after the request.

### A2 — P1: direct break-glass execution violates the proposed DB constraint

**Plan:** [plans/v2/40-support-account-actions.md:244](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:244) and [plans/v2/40-support-account-actions.md:386](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:386).

A direct run sets `requested_by = approved_by = actor`, with mode `break_glass` for an out-of-tier admin. The SQL check requires those two IDs to differ for **every** `break_glass` row. The permitted admin direct run therefore fails its insert.

**Correction:** separate execution mode (`direct`/`approved`) from a `break_glass` flag, or use distinct modes. Enforce two-person separation on approved requests while retaining the independently decided direct-admin path. Test the exact persisted row shapes, including null approver handling.

### A3 — P1: malformed success responses can cause a destructive action to be repeated

**Plan:** [plans/v2/40-support-account-actions.md:178](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:178).

The outcome table treats unparseable `2xx` as `failed`, and the retry design creates a new request with a new outbound idempotency key. An external app could successfully execute an action and return malformed JSON; retrying as a new request can execute it again. Receipt of an invalid success response is an ambiguous outcome, not proof of failure.

**Correction:** classify malformed success bodies and malformed replay responses as `unknown`. Define exactly which error responses guarantee no side effect. Reconcile uncertain requests through a receiver status/result lookup or explicit human resolution before any fresh execution. Retain the original idempotency identity while reconciling.

### A4 — P1: request routing, identity binding and expiry notification need durable recovery

**Plan:** [plans/v2/40-support-account-actions.md:191](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:191), [plans/v2/40-support-account-actions.md:232](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:232), [plans/v2/40-support-account-actions.md:266](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/40-support-account-actions.md:266).

The request is inserted as pending before escalation and before `approver_team_id` is stored. A crash can strand an unrouteable request; returning the existing row on `client_request_id` replay does not finish routing. Expiry commits before `createNotification`; a crash in between permanently loses the notification because subsequent sweeps no longer select that row.

Identity is read at execution time, while only a customer principal reference is saved. The ticket requester, external ID/email or connected-app URL can change between review and execution. The approval may then execute against a different account or endpoint from the one reviewed. The plan also reads email only through `user`, leaving cold-email requesters with `contactEmail` but no user unable to use account actions.

**Correction:** make routing a resumable state with durable completion markers; enqueue expiry notification transactionally with a deduplication key. Bind approval to a defined identity/configuration version or snapshot and require reapproval on material changes. Define cold-email account-action eligibility and receiver-side verified identity requirements. Preserve the distinction between configuration-driven execution and arbitrary caller-supplied identity.

### P1 — P2: framework-switch behavior needs a precise definition

**Plan:** [plans/v2/50-prioritization-scoring.md:153](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/50-prioritization-scoring.md:153).

The SQL re-evaluates `needs_rescore` from the post's **current** status on every read. A post that needed re-scoring at the switch becomes a valid legacy score merely by moving to Planned, without being rescored. A Planned post moving back to Under Review becomes invalid. This may be intended, but it is different from persistently marking the Open/Under Review cohort at switch time.

“Keep their old score” currently means recompute with the old formula and **live votes**, not freeze its value. The SQL also lacks the declared `compatibleWith` branch. The plan says mixed-framework numerical sorting is accepted in one section but leaves that choice open as NEW-P10.

**Correction:** decide dynamic versus switch-time invalidation, frozen versus live legacy scores, compatible versions, and mixed-framework ordering. Send expected framework/version with saves and lock/check config and post status so a stale form cannot silently save under a changed formula. Add a batch/list MCP contract for tower portfolio instead of assuming `get_details` exposes scores.

If revenue-weighted Reach is selected, its cache must also react to company MRR edits, customer-company reassignment and identity merges, not just vote/merge events. Company-counting/deduplication and the cache's rebuild contract need definition. The “registry entry only/no rework” language is too strong for that option.

### N1 — P2: first-visit embed identity and long-lived refresh are incomplete

**Plan:** [plans/v2/60-announcements-banner.md:257](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/60-announcements-banner.md:257).

The banner may mint a viewer token with `principalId: null` before widget identify creates the user. The subsequent widget `identify` event only refetches the feed; a token still naming no principal will continue to have no segment memberships unless the feed explicitly re-resolves the identity or a new token is issued. That conflicts with the stated immediate segment parity.

The viewer token lasts 12 hours, while the widget identity token normally lasts five minutes. A long-lived page needs a defined way to obtain a fresh host-signed token after viewer-token expiry. Reconnecting the two-minute stream token alone does not solve this. Evidence: [apps/web/src/lib/server/widget/identity-token.ts:3](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/widget/identity-token.ts:3).

**Correction:** re-resolve/re-exchange after identity creation/change, clear content and streams on logout/account switch, and define a host token-refresh callback. Test banner-before-widget initialization, account switching, expiry and deleted/recreated principals. State what the banner-only embed does for an identity not yet known to Quackback.

### N2 — P2: resolved-status banners use the wrong source

**Plan:** [plans/v2/60-announcements-banner.md:184](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/60-announcements-banner.md:184).

The plan reads `activeIncidents` and `upcomingMaintenance` then maps recently resolved incidents to success. The active query excludes resolved incidents. Resolved incidents are in `recentIncidents`, whose window filters by **startedAt**, so even that collection can omit a long-running incident resolved within the last hour. Evidence: [apps/web/src/lib/server/domains/status/status.public.ts:182](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/status/status.public.ts:182), [apps/web/src/lib/server/domains/status/status.public.ts:217](/Users/adamstavely/Documents/GitHub/quackback/apps/web/src/lib/server/domains/status/status.public.ts:217).

**Correction:** define an audience-filtered resolved-at query or a suitable domain helper. Include status-derived expiry and maintenance lead-window transitions in `nextTransitionAt`. Confirm whether five-minute incident latency is acceptable; it is separate from instant announcement updates.

### N3 — P1: announcement audit is best-effort despite the durable dual-audit requirement

**Plan:** [plans/v2/60-announcements-banner.md:360](/Users/adamstavely/Documents/GitHub/quackback/plans/v2/60-announcements-banner.md:360).

The plan uses `recordAuditEvent`, which catches insertion failures and returns successfully. The announcement may commit without its required tenant audit record. The account-actions plan already recognizes this and uses `recordAuditEventInTransaction`. ## Preserving upstream upgrades

The design should promise **a maintained, tested fork that can take upstream releases**, not conflict-free upgrades. Sidecars avoid journal collisions and most schema edits, but their foreign keys and queries still depend on upstream tables. Fork code imports non-public domain internals, and the team-RBAC design occupies a reserved upstream column. These are semantic dependencies even when Git merges cleanly.

Before implementation, revise the affected contracts above and add the necessary seams rather than avoiding essential fixes to meet a small seam count. During each upstream upgrade:

1. Review changes to every used domain contract, role resolver, assignment writer, authentication flow and FK target, including unchanged seam call sites whose callees changed behavior.
2. Regenerate structural snapshots, then run negative authorization and feature contract tests; an updated golden file alone is not proof of safety.
3. Rehearse both an empty install and an upgrade of a populated **fork** database, not just upstream/fork drift from empty. Include fork-only releases, old-code/new-schema operation, suspended tenants and failure recovery.
4. Gate deployment on image contents, both migration ledgers, catalogue seeding and workspace isolation. Give each seam/contract an owner and a test.

Recommended sequence remains foundations → RBAC → prioritization → tiers → account actions, with local announcements independently after foundations and fleet infrastructure/SSO spikes early. The tower's full product surfaces should wait until their permission and tool contracts are proven. No finding requires abandoning the fork strategy, but some require more upstream seams than the plans currently budget.
