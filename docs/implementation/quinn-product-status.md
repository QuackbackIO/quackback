## Step 3: durable intent, snapshots and publication fences (P1, P2)

Implemented:

- Migration 0287 adds `assistant_runs` (one live parent enforced by a CHECK, a unique trigger key, a partial unique index over executing runs, status/phase/outcome vocabularies, input revision, state version, diagnostic job id and lease token, bounded attempt and token counters), `assistant_run_steps`, `assistant_run_evidence`, an immutable `assistant_effective_snapshots` keyed by content hash, `conversations.assistant_revision`, a nullable `conversation_messages.assistant_run_id` with a partial unique index allowing one terminal customer-visible message per run, and `assistant_request_receipts` for the HTTP retry boundary. Expand-only.
- `requestAssistantTurn(tx, ...)` runs inside the transaction that persisted the customer message: it bumps the invalidation counter, supersedes older uncommitted runs, writes the run intent and enqueues the turn job with `maxAttempts: 1` on the same transaction. A rollback leaves no run and no job.
- `advanceAssistantRun(job)` claims execution ownership using the queue's lease token, persists the effective snapshot, generates through the existing orchestrator gates, and holds no transaction across the model call. `commitAssistantOutcome(tx, ...)` verifies the input revision, the run status, the run's lease token, the queue row's own lease, the run state version, closed/snoozed/paired/handed-off state and the absence of a terminal message, then commits the transcript message, the run result, the involvement update, the inactivity ownership (migration 0284's trigger derives it from the same insert) and the outbox event together.
- One lock order is documented and used by claim, publication and recovery: conversation row, then run row, then job row.
- Invalidation rides each transition's own statement: customer message, teammate reply, assignment, team assignment, handoff, status change, close, reopen, snooze, wake, spam filing, restore from spam, assistant auto-close, inactivity follow-up and close, and message deletion.
- `ASSISTANT_EXECUTION_MODE` selects `durable` (default) or `legacy`. Legacy restores the previous post-commit fire-and-forget call unchanged.
- An optional `clientMutationId` on the visitor send contract is claimed in the same transaction as the message, so a retried first send returns the original conversation and message instead of creating a second thread. The receipt is bound to a request digest; the same key with different content is rejected. Clients that omit it are unaffected.
- The visitor stream falls back to the durable run row when no ephemeral activity trace exists, so a reconnect after a worker death still shows a turn in flight. Lifecycle only: no trace text, evidence or model detail.

Validation: 14 cases in `assistant/__tests__/assistant-run.durability.db.test.ts` (11 fence and concurrency cases plus 3 that drive the executor end to end with a barriered fake model) and 3 retry-boundary cases in `conversation/__tests__/conversation-request-receipt.db.test.ts`, all on real PostgreSQL with committed transactions, independent connections and the real queue lease and reaper. Each fence was checked by disabling it and confirming the matching case fails. These suites run against a dedicated `quackback_quinn_runs` database, following `conversation-inactivity.db.test.ts`: they commit rows on purpose, and several suites sharing a database assert whole-table state. Create and migrate that database before running them; they are inert against any other `TEST_DATABASE_URL`.

Effective gates: durable execution is on by default for widget-source customer turns only. Workflow `let_assistant_answer` still uses the legacy executor; durable delegation is P4. No write-capable retries: the turn job stays at one attempt. The snapshot is captured and correlated to the run; executing _from_ a frozen snapshot is P7.

Rollback: set `ASSISTANT_EXECUTION_MODE=legacy`. New customer messages stop creating run intents and resume the previous post-commit call. Outstanding unpublished runs are fenced on their own attempt (the invalidation counter has already moved, or the conversation state check refuses them) and can be cancelled explicitly with `cancelOpenAssistantRuns`. Already-committed transcript and delivery work stays durable. The schema and receipts are additive and remain in place; reverting the code does not replay historical messages.

Remaining in this area: durable workflow delegation and recovery sweeps (P4), replayable tool receipts and approvals (P3), run inspection surfaces (P8), and the semantic validator (P6). Cold inbound email and GitHub inbound mutate conversations with direct inserts and do not bump the counter; neither can carry a durable Quinn run today, because the automatic turn gate requires `source = 'widget'`.

## Step 4: connection policies independent per use (connection gate)

Implemented:

- Migration 0288 adds `connectors.profile_policies`, `connectors.tool_reviews`, `connectors.catalog_revision`, `connectors.policy_version` and, on `assistant_pending_actions`, `origin_profile` and `policy_version`. Expand-only and replay-safe: every statement is `ADD COLUMN IF NOT EXISTS`, so a second run against a database that already carries the effect changes nothing.
- Policies are keyed by use (`agent` for customer conversations, `copilot` for teammates, `workspace` for the linked surface). Resolution runs the hard availability gates first (reviewed contract, enforceable input schema), then the exact per-tool override, then that use's group default. A use with no record of its own resolves to never; it never reads another use's record. New records start at reads always, writes approval.
- The old shared map is projected into the uses a connector is ALREADY assigned to, never into others, with provenance recorded on each projected record. The migration carries no backfill because it must replay as a no-op, so the projection runs lazily in code on first read (`ensureConnectorPolicyState`), with NULL as the "not projected yet" sentinel and a `coalesce` write so a concurrent reader cannot clobber it. Deployments that never read a connector row leave it unprojected and unreachable, which is the same answer.
- Discovery no longer lets a new tool inherit a group default. Each tool carries a reviewed contract (input schema hashed over canonically sorted keys, plus the read-only and destructive hints), and a tool that is new or whose contract moved is unavailable to every use until an authorized teammate reviews it. Tools a connector already had are grandfathered at their current contract, and that baseline is persisted rather than derived, so a change made after the gate shipped is still visible. The catalog revision moves only when something actually changed, and a review is refused when the revision has moved since the page was rendered.
- Input validation is exact and runs before dispatch: enums, integer-ness and bounds, nested objects, array items and lengths, required properties, and a 32 KiB ceiling on the serialized payload. The supported-construct policy is explicit and closed: `$ref`, `allOf`, `patternProperties`, conditionals, a schema-valued `additionalProperties` and any unknown keyword make the tool unavailable rather than silently permissive. A remote `pattern` is only run under length bounds. The same subset drives the model-facing zod schema, so the model is not shown a looser contract than the one enforced; a schema outside the subset keeps the previous permissive conversion, which is what the first-party workspace MCP catalogue still uses.
- Dispatch rechecks. Before opening a session the call site re-resolves the current policy for its use and refuses when the connector was disabled, unassigned, re-discovered with a changed contract, or set to never since the turn was assembled.
- A proposal records the use it was made under and the connector policy version at that moment. Approval re-resolves THAT use, read from the row rather than from the approver, and refuses with `ASSISTANT_ACTION_POLICY_CHANGED` when the use now says never or the contract is unreviewed. A customer-origin request therefore keeps customer scope through human approval.
- Policy writes carry the version they were edited from and are refused when it has moved (`CONNECTOR_POLICY_CONFLICT`); a write with no base version at all is refused too. The submitted map is a patch, so a client that sends one column cannot reset the other by omission. The editor keeps its draft when a write is refused.
- The Connections page shows one column per use with the group default above it and a reset to that default in the same control, a review banner naming what moved with a Mark reviewed action, an unavailable row for a tool whose input schema cannot be enforced, and a Needs review marker on the connections list. `reviewConnectorToolsFn` is new and gates on `assistant.manage`, like every other connector write; the authorization matrix and migration contract documents are regenerated.
- The effective snapshot records each connector's policy version, catalog revision and a hash over its per-use policies and reviewed contracts, so a run stays explainable after somebody edits permissions.

Validation, all against `quackback_quinn_validation`: 78 connector tests in `connectors/__tests__`, including 32 on real PostgreSQL in `connector-policy.db.test.ts` covering the 3x3 customer/teammate matrix, the lazy projection, missing-record denial, the review gate, stale-version conflicts, approval re-resolution and the dispatch recheck. The whole affected area passes with no failures: 830 assistant tests (17 skipped, all live-model), 1,769 conversation/workflows/jobs (32 skipped, 1 todo), 2,084 functions/policy/shared-assistant, 631 admin-automation and conversation component tests, and 328 packages/db tests. Each gate was checked by disabling it and confirming the matching cases fail: a cross-use fallback in the resolver fails 3, forcing `reviewed` true fails 4, dropping the schema-change comparison fails 2, and dropping the version or the draft in the editor fails 2. The schema converter was proven red first: the two cases asserting the model-facing contract carried the enum, the integer bound, the nested object and the array items failed against the old converter while the 22 new validator cases passed. Application and workspace typechecks pass, the fresh-database drift check reports no drift, the production build succeeds and the server-function manifest has 826 entries and 826 call sites.

Effective gates: per-use resolution, the review gate and exact validation are on for every connector, with no selector. There is no flag to restore the shared map. Existing connectors keep working because their tools are grandfathered and their policies are projected into the uses they were already assigned to; a connector added after this step starts with every tool unreviewed, so the setup flow is connect, discover, review, then use. A tool whose input schema this workspace cannot enforce becomes unavailable even though it was callable before, which is the intended direction and is reported on the page with the reason.

Rollback: revert the code. The columns are additive and can stay; old code ignores them and resolves the shared `tool_policies` map again, which means reverting is not a policy-preserving rollback for a workspace that has since set different customer and teammate policies, because the shared map is the pre-Step-4 value. Nothing rewrites history, and pending proposals keep their recorded origin use.

Remaining in this area, deliberately: customer subject binding for external reads is NOT implemented, so a workspace credential is still broader than one customer's rights. The specification's own default for a reviewed account-scoped external read depends on that binding; this step ships the policy structure that can express it and leaves the enforcement to the adapter work, so a customer-facing external read remains an operator decision rather than something the product claims to scope. The workspace use has policy records and resolution but no editor on this page; it is edited through the linked surface's own settings. `policy-dial.tsx` is no longer rendered by the connector page, which now uses the shared select, and its own test still covers it. Replayable receipts and queued approvals for these tools are Step 5.

## Step 5: recoverable tools and durable approvals (P3)

Implemented:

- Migration 0289 extends both action tables, expand-only and replay-safe (every statement is `ADD COLUMN IF NOT EXISTS` or `CREATE INDEX IF NOT EXISTS`, foreign keys declared inline with their names spelled out). `assistant_tool_calls` gains the run and step it belongs to, `action_key`, `args_digest`, `schema_digest`, the bounded normalized `result`, `provider_receipt`, `provider_idempotency_key`, `dispatched_at`, `settled_at`, `outcome_status`, `retryable`, `reconciliation_state`/`note`/`at`/`by`, and `replay_strategy`, plus a partial unique index on `action_key` and a partial index over the reconciliation queue. `assistant_pending_actions` gains `run_id`, `run_step_key`, `requested_by_id`, `action_key`, `args_digest`, `contract_digest`, `approved_args_digest`, `execution_state`, `execution_job_id`, `execution_error` and `disposition`, plus a partial index over executions still owed.
- Neither status vocabulary moves. Both tables carry a CHECK listing their statuses and widening one needs a DROP/ADD constraint pair that cannot replay, so the new lifecycle rides its own columns. That is also what keeps older readers safe: a dispatched-but-unconfirmed effect reads as `started` to anything that predates `outcome_status`, never as a success. The one state that has no word in the old vocabulary, a proposal replaced without a decision, is `expired` with `superseded:<reason>` in `disposition`, which is what the surfaces read first.
- `ToolOutcome` (`tool-receipts.ts`) is the shape every tool result is adapted into at the wrapper boundary: `succeeded` with the stored result, `denied`, `pending_approval`, `in_progress`, `failed` with a retryable flag, and `unknown` with reconciliation required. `replayOutcomeFor` is the specification's duplicate-call table as one pure function over a receipt, so it is testable without a fixture.
- The logical action identity is `parent:engagement:tool:argsDigest`, never the model's tool-call id or the job id. The involvement is the engagement when there is one, because it spans the approval wait and every continuation after it. An approved proposal's identity is `pending:<id>`: the decision is the boundary. The claim insert conflicts on the action key as well as on the per-turn idempotency key, so two workers that computed the same business action cannot both dispatch it even when their turn keys differ.
- Anything whose effect leaves this database is stamped `dispatched_at` BEFORE the call, which is the intent commit. A crash in that window therefore leaves a row that says attempted-and-never-confirmed, and `replayOutcomeFor` reads exactly that shape as `unknown`. A built-in local write is not stamped: it and its receipt are written by the same process against the same database, so an interruption leaves neither and the outcome is a definite, retryable failure.
- `replayStrategyFor` classifies a spec: a read has nothing to recover; anything reaching a remote or an MCP session is `external_uncertain`, because neither offers an idempotency or status-query contract this code could rely on; the remaining built-in writes are `local_transactional`. `external_idempotent` exists in the vocabulary and is currently unreachable, because no shipping connector accepts a key we supply.
- A fulfilled promise is no longer evidence. `ok: false`, `isError`, a declared no-parent no-op and every tool-specific failure envelope settle as `failed` with `retryable: false`, never as a success, in the audit row and in the outcome the model is handed.
- `decideAndEnqueuePendingAction` records the decision and enqueues the execution job in ONE transaction, deduplicated on the action id. Approving no longer executes inside the request: `approveAssistantActionFn` returns approved-and-queued as soon as the row moves. The `assistant-action` queue (concurrency 2, `maxAttempts: 3`, 120s lease) is the only Quinn queue that retries, and it is safe to because execution is claimed on the receipt's action key, so a second attempt reads the first attempt's receipt instead of dispatching again.
- The worker re-resolves everything at the moment of dispatch: the approver's live actor rebuilt from their principal row, the parent's visibility, the connector policy under the proposal's own use (never the approver's), the tool's presence and risk, the contract digest, the live zod parse, the approved argument digest, and every permission the tool declares. Each refusal is recorded as `refused:<reason>` with a reviewer-facing note, and nothing is dispatched.
- A turn that left a live proposal behind parks its run in `waiting_action` and releases the worker. The result arrives as its own continuation run rather than a resumption, which is what stops a customer message during the approval from stranding the action: the parked run is superseded in the ordinary way while the proposal stays decidable. `getOpenRunState` no longer reports `waiting_action`, so a parked run does not leave a typing indicator running for the length of the approval.
- `ownershipForActionResult` settles the parked run and routes the result under the conversation lock, in one transaction. Quinn still owning it means a continuation turn with an instruction that matches the real outcome (`succeeded`, `failed`, `unknown`, `refused`); a teammate having taken over means an internal note instead, and no continuation at all, so a provider callback cannot hand ownership back.
- A proposal from an earlier durable run for the same item and the same tool is superseded when a later turn proposes that tool again. Two proposals of one tool inside a single turn are two different requests and both survive. Only an undispatched proposal can be replaced.
- The inline card renders the review decision and the execution as two separate readings and asserts nothing about the customer outcome, which is the thread. Approved-and-queued therefore renders as approved and queued. The row polls only while an execution is in flight. An unconfirmed execution offers a person's verdict with a note, and there is deliberately no repeat button.
- Needs approval is a new built-in inbox view in the AI section with its own column, because a row here is an action rather than a thread: proposals this teammate may decide, and below them the executions nobody has confirmed. Selecting a row opens the parent conversation or ticket. Both halves are scoped per row by the item they hang off, and `listAssistantReviewQueueFn` and `reconcileAssistantActionFn` are classified in the authorization matrix.

Validation, on real PostgreSQL: 22 cases in `assistant/__tests__/assistant-action.durability.db.test.ts` over the three kill points the specification names, plus the approval, ownership and integrity properties around them, and 17 pure cases in `tool-receipts.test.ts` over the duplicate-call table. Each gate was checked by disabling it and confirming the matching cases fail: dropping the `action_key` unique index fails the before-dispatch case; removing the dispatched-with-no-settlement reading fails 3; making an interrupted external dispatch a plain failure fails 2; dropping the approved-argument comparison fails 1; ignoring the assignee fails the after-takeover case; dropping the still-proposed decidability guard fails 2; and removing the supersede call fails 1.

The kill-point suite runs against a database of its own, `quackback_quinn_s5`, and is inert anywhere else. It commits rows on purpose, and it does not share Step 3's `quackback_quinn_runs` because a continuation enqueues an `assistant-turn` job, the poller is FIFO per queue, and vitest runs the two files in parallel workers; separate databases are the only cleanup that does not depend on timing. Create and migrate it before running them.

Suite counts, all green: 849 assistant tests (39 skipped, live-model), 1,770 conversation/workflows/jobs (32 skipped, 1 todo), 2,084 functions/policy/shared-assistant, 761 admin-automation and conversation component tests, 2,995 across components/client/routes, 328 packages/db, 94 fleet, and 22 plus 14 in the two durability suites on their own databases. Application typecheck passes, `db:check-drift` reports no drift on a fresh database, the replay classifier calls 0289 `safe`, the production build succeeds, and the server-function manifest has 828 entries and 828 call sites (826 before, plus this step's two).

One pre-existing failure was found and fixed rather than reported around: `fleet/__tests__/migrator-gate.test.ts` enumerates the post-0248 replay span by hand and still stopped at 0286, so it had been red since 0287 and 0288 landed in Steps 3 and 4. All three names were added.

Effective gates: replayable receipts and the normalized outcome are on for every tool, with no selector. Durable approval execution is on for every proposal, because the decision and its job commit together and there is no second path. Durable write execution through the receipt contract is enabled only where a receipt means something: built-in local writes commit with their receipt, and an interrupted connector or MCP write becomes `unknown` and waits for a person rather than being resent. The `assistant-turn` queue still runs at one attempt; receipts are replay-safe now, so the remaining reason is the one P4 names, confirming durable customer mode under two workers before a second attempt may generate into the same conversation.

Rollback: revert the code. The columns are additive and can stay; old code ignores them, approves inline again and settles the same rows. Two things do not come back on their own. An approval decided but not yet executed leaves a queued `assistant-action` job nothing will claim, so those rows stay `approved` with `execution_state = 'queued'` and need either the new code back or a manual decision. A receipt already marked `unknown` keeps its reconciliation state, which the reverted UI cannot show; the row is still correct, and nothing reads it as a success. `ASSISTANT_EXECUTION_MODE=legacy` still stops new durable intake and therefore new parked runs, but it does not stop the approval queue, which is independent of it.

Remaining in this area, deliberately: the customer-outcome dimension is not asserted by any control this step ships. It lives on the involvement and the thread, and a card that printed it would be guessing; the card shows the decision and the execution and stops there. A provider status lookup for an unknown dispatch is not implemented, because no connector offers one, so `external_idempotent` stays unreachable and every uncertain write goes to manual reconciliation, which is the specification's own default. Reconciliation has no bulk action and no filter beyond the two lists; a workspace with many unconfirmed effects will want one. The recovery sweep over stranded `queued` executions is not built here: the job queue's own reaper covers a dead worker, but a job row lost with its queue retention would leave an approved action nobody re-enqueues, and that sweep belongs with P4's recovery work. Workspace-thread proposals have no inbox parent, so they appear in neither half of the Needs approval queue.

## Step 6: workflow delegation and lifecycle waits (P4)

Implemented:

- No migration. The delegation identity rides `assistant_runs.delegation`, which Step 3's 0287 already added, and the wait's own half rides the run cursor, which is jsonb. Slot 0290 is still free.
- `let_assistant_answer` no longer launches a turn. The action checks eligibility, which is a read, and returns the delegation to the engine; `parkAtAssistantWait` then writes the wait, the run intent and the turn job in ONE transaction. That closes the race the specification names: a turn started before the park could hand off while the run was still `running`, and the completion had no wait to resume. A park that cannot commit both halves interrupts the run rather than leaving a wait nothing can answer.
- The delegation identity is `{workflowRunId, nodeId, waitSeq}`, and its trigger key `workflow:<run>:<node>:<visit>` is the per-step receipt P4 asks for: keyed by workflow run, node and visit rather than node alone, and unique, so a replayed park (a retried wait job, a re-walked resume) resolves to the same run instead of delegating twice. The wait cursor carries `delegatedRunId` and `expiryCeilingAt` alongside the existing fields.
- Later turns in the same engagement inherit the live wait. `requestAssistantTurn` reads it from the workflow run (`findLiveAssistantDelegation`), not from the previous run, so a workflow that has moved on hands out no identity, and a hand-off three customer turns after the delegation still resumes the right wait.
- Completion is correlated. `completeAssistantDelegation` claims the wait only while its sequence still matches, so a run that finished late, after the workflow moved on or parked again, resumes nothing. `assistant.handed_off` no longer resumes a delegation-backed wait for the same reason: the event carries no identity. The lifecycle's own signals (`assistant.resolved`, a close) still resume it, as does any wait parked under the legacy selector.
- The wait's meaning is unchanged. An ordinary answer ends nothing, a clarification is still a customer wait, a workflow control block still owns its typed reply, and a visitor message still never interrupts a parked assistant wait. A hand-off, a decline at the gates and a failed execution take the escalated edge.
- Expiry separates an execution that died from a customer who has not resolved anything. `classifyAssistantWaitExpiry` reads Quinn's side of the conversation and returns one of three verdicts: **defer** while a turn is generating, while a run owes an approved action's result, or while Quinn has answered and the customer has not come back; **release**, ending the wait without taking either edge, when a teammate has taken over, when the conversation is no longer open, or when the ceiling passed on a conversation Quinn did answer; **escalate** otherwise, which is the pre-existing default fallback. Deferral extends the deadline by five minutes and is bounded by a ceiling stamped at park time (24 hours), so a live engagement cannot hold the customer-facing exclusive slot forever and no worker is held open for any of it.
- Expiry that removes Quinn's authority fences it in the same transaction. `resumeWorkflowRun`'s new `fenceAssistantWork` option takes the claim and calls `invalidateAssistantWork` together, so a turn that was generating when the wait expired is superseded and its publication is rejected at the revision fence. A release deliberately does not fence: it does not remove Quinn's authority, it only stops the workflow waiting.
- `sweepStrandedAssistantDelegations` is the recovery pass (in `workflow-sweep.ts`, no new queue). A wait whose delegated run is terminal-without-an-answer, or whose run published a hand-off and died before it could say so, or whose turn job was lost entirely while the run sat `queued`, is resumed down the escalated edge with the same fence. A superseded run owes nothing, because a newer turn took over; an answered one owes nothing either. A conversation with any other open Quinn run is skipped, because that run carries the delegation forward.
- Inactivity stands down while Quinn owes a result. The acknowledgement published for a proposal is an ordinary assistant message, so migration 0284's trigger reads it as an answer and starts the assumed-resolution clock; left alone the close pass would record a resolution for an answer that has not happened. Both `dueQuery` and the under-lock recheck in `executeInactivity` now skip a conversation with a run in `waiting_action`, mirroring the interactive-workflow-wait protection beside them. The gate is bounded by the proposal: `sweepAndNotifyExpiredPendingActions` now releases the run parked on a proposal nobody decided, which is the recovery Step 5 deferred to P4.
- Approval still emits no handoff outcome, and a parked approval defers the wait rather than escalating behind the reviewer's back. Both are asserted rather than assumed.

## Step 7: internal feedback capture, safely (feedback gate)

Implemented:

- Migration 0290 adds three columns to `posts`, expand-only and replay-safe (three `ADD COLUMN IF NOT EXISTS`, two `CREATE INDEX IF NOT EXISTS`, the audience CHECK declared inline on its column and therefore skipped with it on a second run). `audience` defaults to `'board'`, which is exactly what every existing row already means, so there is no backfill. `capture_key` carries the logical identity of the capture that wrote the row, under a partial unique index. `capture_provenance` is a small jsonb record of what captured it and from where.
- Audience is a second privacy axis, deliberately not moderation. Pending means "waiting for review", and review can end in publication, which is why the author of a pending post may read it. Internal means "the team's record about this customer", and no later event turns it into something they may read, so the own-post hatch must not re-admit it. `canViewPost` denies it with the same copy an unpublished post gets, so the two cannot be told apart by probing, and `postViewFilter` spells the audience clause as a peer of the board filter rather than inside the moderation disjunction.
- `PostShape.audience` is required rather than defaulted. A reader that forgot to select the column would otherwise read an internal post as a board one silently, and the compiler is the only thing that finds every such reader. Nine call sites were widened: `post.access.ts` (three selects), `post.public.detail.ts`, `post.merge.ts`, `events/targets.ts`, `notification.service.ts`, `comment.service.ts`, and the synthetic post `boardCapabilitiesForActor` builds.

The admin feedback list sees every audience and gains an Internal captures filter.
- `createPost` derives the whole side-effect suppression from `audience === 'internal'` rather than from a flag: no author vote (the row and the count), no subscription, no activity row, no announcement. A future side effect added to that function therefore cannot leak out of a capture by being added before somebody remembers a second flag exists. The caller's `skipDispatch` still composes on top.
- Capture, link and publish are three commands in `posts/post.capture.ts`. Capture writes ONE internal post for the conversation's real customer with Quinn as the capturer and a backlink. Linking attaches a conversation to an existing post and casts no vote, because a link is evidence and voting on somebody's behalf is its own authorized action. Publication takes the reviewed title and body explicitly, so what becomes board-visible is what a person read rather than whatever the capture stored, refuses anyone without both `post.approve` and `post.view_private`, pins the audience in its UPDATE so two reviewers settle on one write, and adds no vote and no subscription. It is the moment the post is announced, which is what makes the dispatch guard's reading honest.
- Idempotency rides the receipt's own identity rather than a second mechanism. Step 5's claim stops a second dispatch but cannot hand back the post: a crash between the post's commit and the receipt's settlement leaves a receipt reading `in_progress` with the created post id nowhere a retry can find it, and the conversion dialog goes through no receipt at all. So the receipt's action key is persisted on the post as `capture_key` under a unique index, which makes the insert itself the idempotent operation. `executeAndSettle` stamps that key on the tool context just before `execute`, and the teammate path derives one from the conversation, board and title. The pre-read is only the fast path; the unique index is the guarantee, and the lost race is collected by catching it.
- The tool contract changed meaning, not just shape. `capture_feedback` is the first built-in to declare a `contractDigest`, and the executor now reads an absent stored digest against a declared one as `contract_changed`. A proposal a reviewer approved under the old "posts publicly under the customer's identity, joins the roadmap" card is therefore refused and re-proposed with the new text instead of quietly doing something else. `POST_VOTE_ON_BEHALF` is dropped from the tool, because the command casts no vote and asking for a permission it cannot use would make the dial look like it controls something it does not. The workspace-assistant branch that called `createPost` directly is gone: it had no customer to attribute a capture to, and using the approver instead answers a different question.

## Step 8: the unified Guidance migration (guidance gate)

Implemented:

- Migration 0291 adds `assistant_guidance_entries` and `assistant_guidance_bindings`. An entry holds one authored instruction at full length with its kind (`always`, `situational`, `procedure`), its owner, its enabled state, its priority, its revision and its migration provenance; a binding attaches it to exactly one existing profile under a unique `(entry_id, profile)` index. A shared instruction is therefore two bindings over one body, which is what leaves no place for a "both" role and no second copy of the text to inject twice. Expand-only and replay-safe: two `CREATE TABLE IF NOT EXISTS` with every constraint inline (the bindings foreign key is named explicitly, because the derived name exceeds PostgreSQL's 63-character identifier limit and comes back truncated, which the drift check reads as drift), `CREATE [UNIQUE] INDEX IF NOT EXISTS` for the rest, no `DO` block and no backfill.
- The conversion runs in code, once per workspace, idempotently, on first read (`guidance-conversion.ts`), for the reason Step 4 established and this step needed more of: a replayed statement may not run a backfill twice, and this conversion has to carry each legacy row's creation instant (the prompt orders candidates by it), its exact per-role scope, and bodies up to 8,000 characters. Idempotency is the database's, not the code's: `(legacy_source, legacy_id)` is unique, every insert is `ON CONFLICT DO NOTHING`, and two processes converting at the same moment agree without a lock. Three small indexed reads decide whether there is anything to convert at all, so a converted workspace pays only those.
- One store answers a runtime read, chosen by `ASSISTANT_GUIDANCE_SOURCE`. `canonical` is the default; the exact word `legacy` is the rollback position and anything else resolves to canonical, so a typo cannot quietly select it. `listEnabledGuidanceCandidates`, the procedure catalogue, a procedure body and the procedure count each branch once, and neither branch falls back to the other.
- The writing guidelines stay owned by the versioned assistant config. The config is what still renders them in its own prompt block, their edits still go through the config write funnel with its revision and managed-field checks, and their canonical row is a projection the runtime never reads back, which is how the same instruction cannot arrive twice. The managed workspace and Slack instructions are projected the same way and are read-only. The Guidance list read is what refreshes both, so nothing has to run on the turn path to keep them current.
- The Guidance editor writes canonical entries. A new entry can apply to customer conversations and support teammates at once, because the entry and every binding are one transaction rather than two writes that could half succeed; the single-use picker and the copy explaining why it was single-use are gone. Saves carry the version they were read at, the row is locked and the version compared and bumped inside the same transaction as the bindings, and a refused save keeps its draft. Deleting an entry takes its bindings with it through the declared cascade. Filters, search, selection-change confirmation and the concurrent-delete error are unchanged.
- Runtime budgets are explicit and in one place (`GUIDANCE_RUNTIME_BUDGETS`): 25 candidates, 5 selected conditionals, 4,000 characters of instruction, a 2,000 character procedure catalogue, 3 procedure loads a turn, an 8,000 character body. An instruction the character budget cannot fit is reported rather than silently dropped: `selectWithinGuidanceBudget` returns what it omitted and the turn records `guidanceOmittedIds` beside `guidanceAppliedIds`, so an authorized inspection can say an instruction was left out for room rather than for scope.
- The effective snapshot records each guidance entry's and procedure's id and version, plus which store answered. Two runs sharing an id and a version read the same instruction even after the text has moved on; a run recorded under the rollback reader carries the legacy ids and version 0, which is what the legacy tables can honestly say about themselves.

## Step 9: retrieval and answer quality (P5, P6)

Implemented:

- Migration 0292 adds `assistant_knowledge_sources`, `assistant_source_versions` and `assistant_chunks`: a derived search projection over the help-center articles, uploaded documents and web pages that already exist. It owns nothing. Every read joins back to the row it projects and applies that row's own visibility predicate and use switch, so a category turning private, an article being unpublished, a document being soft-deleted or a customer-use switch being turned off removes its passages from the very next query, with no reindex and no copied audience tag that could go stale. Expand-only and replay-safe: three `CREATE TABLE IF NOT EXISTS` with inline, explicitly named constraints (the derived foreign-key names exceed PostgreSQL's 63-character limit) and `CREATE [UNIQUE] INDEX IF NOT EXISTS` for the rest, and no backfill. `active_version_id` deliberately carries no foreign key, because the two tables reference each other and a circular inline constraint cannot be written in a file that creates them in order; activation flips both in one transaction.
- A passage is both the unit that matches and the unit that is supplied, which is the whole point. The old shape embedded a source's first 8,000 characters and handed the model its first 1,200, so a fact further down was unreachable even when the row itself matched. `chunking.ts` is pure and deterministic: paragraph boundaries where it can, sentence then word boundaries inside an oversized paragraph, a heading path carried as context rather than pasted into the text, and offsets exact enough that `source.slice(charStart, charEnd)` is the passage.
- `knowledge-index.service.ts` stages a generation nothing reads, embeds every passage, then activates in one transaction that supersedes the old generation and points the source at the new one. With embeddings configured, a failure on any passage fails the whole generation: the previous complete one keeps serving and the reason is a row rather than a gap, and a first-ever failure leaves the source unavailable and labelled. With no embedding model at all the generation is lexical and records itself as `embeddings_unavailable` rather than pretending to have vectors. The embedding model is recorded per generation and per passage, so a model change produces a new generation and the vector arm skips any generation another model built: equal dimensions do not imply a compatible space.
- The `assistant-knowledge-index` queue runs at concurrency 1 with three attempts and a 120s lease, and handles one source or a bounded backfill page. The backfill needs no cursor: requesting an index writes the projection row before the work runs, so a claimed source leaves the unindexed query immediately and a dead pass resumes exactly where it stopped. A daily cron is the resumption point, gated in the same module as the handler, so a workspace whose corpus is fully indexed writes no row and wakes nothing. Article, document and web-page writes request an index with a durable source revision; their deletes tombstone it. No object storage is required anywhere: a document's extracted text is already the grounding source of truth and is what gets chunked.
- Retrieval asks the index first. A source with an active generation is answered by its passages and one without is answered by its existing whole-source adapter, and nothing is answered twice, so a partially backfilled workspace loses no recall. Lexical and vector candidates are retrieved independently and merged by rank, using the same `mergeByRank` the composer uses across sources (extracted, not re-implemented), and the passage is supplied uncut, because cutting it would undo the reason the index exists.
- One query embedding per turn, resolved once by the composer and passed to every adapter. It is passed rather than cached, so an adapter's behaviour never depends on an earlier turn and an adapter called directly still resolves its own. Nothing in that path may throw: a turn that cannot embed its question degrades to the lexical arm and records `embeddings_unconfigured`, `embedding_failed` or `embedding_dimension_mismatch`, which is what stops a degraded turn from looking like a corpus with nothing relevant in it.
- The KB adapter honours the requested candidate budget. Raising the outer topK previously left its inner five-result pool untouched; four pinned call-shape assertions were updated, which is the fix they were pinning against.
- The evidence package reaches the run. Every search records the exact passages it supplied, in supply order; the turn returns them with the citations the answer kept mapped onto them, and the executor hands them to `commitAssistantOutcome`, which persists them on Step 3's `assistant_run_evidence`.
- The deterministic publication validator (`publication-validation.ts`) is pure and always enforced, under the publication fence: empty or oversized text, a citation kind outside the canonical eight, a citation the turn never retrieved, an internal citation or internal evidence, a source revoked while the turn was generating, a response kind that is not publishable, and a candidate closing the conversation while this run's own receipt says the effect never settled. Two of those are statements about the present, which is why the check runs at publication rather than after generation. Revocation is rechecked through `getCustomerCitationSource`, the same function the customer-facing citation endpoint serves from, so the answer and the link the customer clicks cannot disagree; it fails closed. Each verdict is written to the run's step ledger either way, so a refusal reads as a validator decision rather than as a turn that produced nothing.
- The semantic verifier (`answer-validation.ts`) asks what no rule can: whether the material claims follow from the evidence, and whether action claims match receipts. Verdicts are the specification's five, stored with a bounded one-sentence reason and the evidence ids it leaned on; no chain of thought is requested or kept. `ASSISTANT_ANSWER_VALIDATION` selects off, shadow or enforce, shadow is the default, and an unrecognised value resolves to shadow rather than to enforce. It rides the existing quality-gate model resolution and stands down with `no_quality_gate_model` recorded when a deployment has none, so a single-model BYOK install is a recorded absence rather than a silent pass. A greeting, a clarification and a hand-off make no product claim and are not asked for evidence. In enforced mode a refusal gets exactly one constrained repair, read-only by construction (the repair pass assembles no write tool at all, so it cannot repeat a business write whatever the model decides); a candidate still unsupported, or a verifier that errored, goes to the existing handoff floor and is never recorded as a resolution.
- The effective snapshot records the retrieval configuration (registered source types, embedding space, parser and chunker versions, candidate budget) and both validator layers, replacing the two placeholders Step 3 left.
- The Knowledge page says whether Quinn can actually read each source, and says nothing when it can: a healthy row is still the name and its switches. Only the states a person can act on are named, and as what Quinn is doing about them: `Update failed, using the last version`, `Not indexed`, `Indexing`, `Keyword search only`. Refresh is staged by construction, because the whole projection is.

Remaining work and deliberate omissions:

- Only the three long-form source types are indexed. Posts, snippets, changelog entries, ticket summaries and conversation summaries keep their whole-source adapters, which is the specification's own staging: they are short or operational, and moving them should follow measured evaluation rather than precede it.
- No rerank stage. The specification offers reciprocal rank fusion and an optional reranker as proposals, not assumed improvements, and the rank-interleaving baseline is preserved exactly (the merge is the extracted original, not a rewrite) so a future comparison has something honest to compare against.
- The approximate index is created but not measured. `assistant_chunks_embedding_hnsw_idx` exists and exact search remains the correctness baseline around it; no query plan or recall comparison has been run, because this branch has no corpus large enough for one to mean anything.
- The semantic verifier has not been calibrated. It ships in shadow mode precisely because it has no reviewed cases behind it yet; graduating it to enforce is a decision for after a workspace has run it, and the run-step verdicts are what that decision reads.
- The repair pass re-answers rather than expanding retrieval. The specification allows either; re-answering with no write tool is the one that is structurally safe, and a retrieval-expansion variant would need its own budget accounting against the turn's iteration cap.
- Chunk-level retrieval has no per-source passage diversity beyond one passage per source. Two passages of the same article would collapse into one citation anyway, but a long document whose answer spans two sections is currently served only its best passage.
- The Knowledge page shows health for documents and web pages, which are the rows it renders. Help-center articles are indexed and served from passages but their health is not surfaced anywhere; the Help Center article screens would be the place, and that is a surface change rather than a backend one.
- `assistant_run_evidence` has no retention pass. The specification asks for one over run steps, evidence excerpts and tool results together, and that belongs with P8's operations work rather than with a single table here.
- The KB adapter still fails closed to an anonymous viewer for the segment gate, and the passage query mirrors that exactly. Threading a verified viewer through the policy API for customer-specific segmented knowledge remains explicitly out of scope, as the specification requires.

## Step 10: evaluated changes and publication (P7)

Implemented:

- Migration 0293 adds `assistant_releases` and `assistant_release_checks`, and two columns on `settings`: the opt-in `assistant_release_management` and the `assistant_published_release_id` pointer. Expand-only and replay-safe: two `CREATE TABLE IF NOT EXISTS` with every constraint inline and every foreign key named explicitly (drizzle's derived name for the snapshot key is 66 characters and PostgreSQL truncates at 63, which the drift check reads as drift), `CREATE [UNIQUE] INDEX IF NOT EXISTS` for the rest, two `ADD COLUMN IF NOT EXISTS`, and no backfill. The settings pointer carries no foreign key on purpose, the same reason 0292's `active_version_id` does not: `assistant_releases` references `principal` in the same module as `settings`, so a constraint the other way closes a cycle. Publication moves the pointer and the release row's status in one transaction instead. One draft and one live release are enforced by partial unique indexes rather than by a read-then-write two publishers could both pass. The check-status CHECK spells all six verdicts although the runner produces four, because widening a CHECK later needs a DROP/ADD pair that cannot replay.
- A release references immutable, content-hashed snapshot content, which is what makes it survive any pruning a versioned-history table does. The candidate hash IS the effective snapshot's content hash, so it covers the configuration, the guidance entry and procedure versions, the connector policy versions and contract fingerprints, the retrieval configuration and both validator layers. Anything that moves Quinn's behaviour therefore moves the candidate and invalidates its evidence, which is the conservative direction: the gate can be too eager, never too relaxed.
- The draft is derived, not authored. There is no second store: the draft release points at whatever effective snapshot the settings row resolves to right now, refreshed lazily on every read of the release state, in the same shape Steps 4 and 8 used for their projections. That removes the failure mode where a save commits and the follow-up write that was supposed to refresh the candidate does not.
- Release management is off by default, so an existing install saves immediately exactly as before. Turning it ON publishes the workspace's CURRENT behaviour as its first release first, so the moment of opt-in changes nothing a customer could notice. Turning it OFF makes the settings row live again, which is the pre-release behaviour and the documented rollback; a draft pending at that moment becomes live with it.
- With it on, `getAssistantRuntimeConfig` is answered by the published release's snapshot and the settings row is the draft. The editor reads (`getAssistantConfig`, `getAssistantSettings`) still read the row, so every existing card edits the draft with its existing revision and managed-field semantics unchanged. A release that cannot be read falls through to the row with a warning rather than stopping Quinn, which is the direction every other read in that function already fails.
- Publication compares rather than recomputes. It refuses a candidate that moved since it was reviewed (`ASSISTANT_RELEASE_CANDIDATE_CONFLICT`), a candidate whose required checks are not passing evidence for it (`ASSISTANT_RELEASE_CHECKS_INCOMPLETE`), and a candidate whose config revision has been overtaken by a save, the last compared under the settings row lock because it is the only one a concurrent writer can create after the first two passed. Refreshing the draft inside publish would have hidden that race instead of exposing it, so it deliberately does not.
- Rollback is append-only: it inserts a NEW published release carrying the restored snapshot and naming what it restored, so release numbers never move and the history reads forwards. Numbers are allocated at publication rather than at draft creation, so a rollback published while a draft is open cannot end up numbered below it. Rollback carries the live release the reviewer saw and refuses when it moved (`ASSISTANT_RELEASE_LIVE_CONFLICT`).
- A run SELECTS its behaviour once, at the start, through `selectRunBehaviour`, and carries the frozen configuration through the turn as `runtimeConfigOverride`. Publishing or rolling back mid-generation therefore changes what the NEXT run selects and nothing about the one in flight. With release management off this is exactly the pre-release path: build the live snapshot, attach it, let the turn resolve its configuration live.
- What a release governs is the assistant configuration and only it. Role permissions, connector enablement and per-use connector policies, the per-source customer/teammate switches, a category turning private, an article being unpublished and a soft-deleted document all stay live and immediate. A release preserves how Quinn was configured to speak; it grants nothing and it cannot hold a revocation open.
- Three required-check keys, of which two are required. `configuration` parses and normalizes the candidate and refuses one that moves a managed field. `toolset` assembles the customer and teammate tool sets under the candidate and reports rules naming an action that is not available (reported, not blocking: a connector disabled for the afternoon is a legitimate transient and blocking a wording change on it would teach people to ignore the gate). `answer_sandbox` runs one sandbox turn and is NOT required, which is what "model suites are opt-in" means: a provider outage must not decide whether a workspace may ship a wording change. Without a model it records itself as `skipped` with the reason rather than passing.
- Every result is stored with the candidate hash it was produced against. The gate counts only a `passed` result recorded against the candidate in front of the reviewer; a missing row, a row from an earlier candidate, and every other verdict block, each under its own reason, because "not run yet" and "run and skipped" are different things to read.
- The candidate sandbox reuses the existing admin simulate seam rather than inventing a second one: `runAssistantTurn` with no conversation and `simulate` on. No conversation means no inbox row, no involvement, no transcript message and no realtime event, and every write tool previews before any dial is consulted, which is the ordering Step 7 fixed and this step's tests now hold.
- Test Quinn (`/admin/automation/test`) is the sandbox chat plus the publish review: the affected-use diff, the required checks with their real results, Publish offered only when the gate passes, and the release history with rollback. With release management on the sandbox can ask the same question of the draft and of what is live. Every existing call site is unchanged because the option defaults to absent.

## Step 12: actions, channels and product follow-up (P9)

Implemented:

- **No migration.** Nothing this step needs is a schema change. The procedure steps ride the graph jsonb and the existing receipt and proposal tables; the email channel rides a settings metadata key, the existing delivery record on a message's metadata and the existing threading store; the follow-up rides the receipt table. `ASSISTANT_RUN_SURFACES` gains `email`, which is a TypeScript fact about a plain `text` column with no CHECK, so the drift check reports no drift. Slot 0295 is still free.
- **Two workflow procedure kinds, `call_tool` and `approval`**, reaching Quinn's own action machinery rather than the conversation. Both are receipted by `workflow:<run>:<node>:<visit>`, the shape Step 6's delegation trigger key already uses and for the same reason: a retried wait job or a re-walked resume loses the claim and reads the first attempt's verdict instead of dispatching a second effect. The visit is the run cursor's current `waitSeq`, which is stable across every retry of one resume and moves on the next park.
- **What a procedure step may run is the workspace's own dial**, read through `applyBuiltInToolRules` against the customer agent's `toolRules`, which is the record the Connections page actually edits. A tool set to Never is unavailable to a procedure too, and a tool set to Needs approval cannot be a `call_tool` step at all: it has to be an `approval` step, which is what the dial was asking for. Connector tools are deliberately not offered, because a connector resolves its policy per use and a workflow is none of the three uses; inventing a fourth with no editor behind it would be the fake control this work exists to avoid. Read tools are not offered either, because a procedure step has no model to read the answer.
- **`call_tool` never persists a wait.** Only the engine knows the receipt's verdict, so the walk stops at the node and the engine re-walks from it with the verdict in the same pass; a step that produced no verdict at all reads as failed, so the run takes the failed edge rather than parking on something nothing resumes. Every reading other than a confirmed success takes `failed`, including an effect nobody could confirm, whose receipt stays in the reconciliation queue.
- **`approval` parks** with a fourth wait kind, on a cursor carrying the proposal id. A decision, an execution result or the proposal's own expiry sweep resumes it, correlated on the proposal id and the visit, so a late answer to an earlier visit resumes nothing. Only a confirmed execution is the approved edge: a rejection, an expiry, a refusal at dispatch, a failure and an unconfirmed effect all take `declined`, and the run event records which it was. A visitor message no longer ends an approval wait, for the same reason it does not end an assistant wait.
- **The builder can author both.** A Procedure palette group, one editor shared between the kinds (a tool picker, a key and value argument list, and a reviewer-facing summary for the approval kind), icons, card content on the list and the canvas, tree round trips through the existing fixed-two-path helpers, and the setup-needed chip for a step with no tool or no summary. The picker is driven by a small shared catalogue whose names a test asserts are a subset of the built-in write tools that fit a conversation parent, with each listed argument a key that tool's own contract declares. The argument ceiling the builder enforces is refused at the save boundary too.

The orchestrator's existing `messenger.assistant.respond` gate still applies on top, so autonomous email needs both.
- **Delivery is durable and separate**, following the inactivity follow-up exactly. The answer and its `pending` delivery record commit in the publication transaction and a new `assistant-email-delivery` job carries it out, so a provider outage delays a delivery rather than losing an answer or holding the publication fence across a network call. The worker asks the same rules again before sending, because a takeover, a close or the switch being turned off between the commit and the send all mean this workspace should not now write to the customer as Quinn; that reads as a recorded cancellation on the message rather than a silent drop. Threading and the recorded outbound Message-ID are the ordinary outbound path's, so a customer reply resolves back to the thread.
- **The Deploy page's Email row reads the real state** instead of describing one. It names what is missing, an inbound route or Quinn answering customers at all, and offers the switch only when neither is.
- **A reviewed product follow-up.** A reviewer opens a board post, reads exactly who would be written to and why each unreachable person is unreachable, writes the update and sends it. Nothing calls it from a status change, a changelog publication or a capture: the team shipping something and the customer being told are different facts. An internal capture refuses the whole action rather than filtering per recipient; a customer with no deliverable address and one who muted email are shown with the reason and cannot be selected. Identity is `followup:<post>:<customer>` through Step 5's receipt service, stamped dispatched before the provider call, so one post and one customer is one email however many reviewers press the button at once, an unconfirmed send joins the reconciliation queue rather than being resent on a guess, and a refusal the provider gave before sending anything is the one reading a reviewer may try again, under the same receipt.
